> 판정: **BLOCK — 현재 설정 페이지를 APP 전체의 신뢰 가능한 제어면으로 간주할 수 없음**

## 1. 요약 결론

현재 설정 페이지가 노출하는 **32개 편집 항목**을 저장 경로에서 실제 소비 지점까지 추적한 결과는 다음과 같다.

| 판정 | 항목 수 | 비율 | 의미 |
|---|---:|---:|---|
| 완전 적용 | 6 | 18.75% | 저장 후 의도한 APP 동작에 직접 반영됨 |
| 부분·조건부 적용 | 8 | 25.00% | 일부 화면/사용자/프로세스에만 적용되거나 지원 범위가 UI보다 좁음 |
| 미적용 | 18 | 56.25% | 저장은 되지만 현재 운영 코드에서 효과가 없거나 실제 소비 경로가 없음 |
| 합계 | 32 | 100% | 설정 페이지의 현재 편집 항목 전체 |

핵심 결론은 다음과 같다.

1. **OEE 설정 7개와 알림 설정 5개는 전부 실질적으로 미적용**이다. 현재 APP은 관련 임계값과 폴링 주기를 여러 코드 위치에서 하드코딩한다.
2. **`모든 설정 초기화`는 운영 장애를 유발할 수 있다.** 라이브 휴식시간은 110분이고 실시간 계산도 110분만 지원하지만, 코드 초기값은 60분이다. 초기화하면 실시간 생산 진행 API가 안전 중단(fail-closed) 상태로 전환될 수 있다.
3. **UI가 허용하는 교대 설정 범위와 실제 엔진이 지원하는 범위가 다르다.** UI는 임의의 서로 다른 시작시각과 0~240분 휴식을 허용하지만, 실시간 계산은 사실상 12시간 교대와 고정 110분 휴식 모델에 결합돼 있다.
4. **언어와 테마 의미가 2026-07-14 이후 바뀌었지만 설정 페이지 표현은 예전 의미를 유지한다.** 이제 시스템 값은 사용자 프로필 값이 없는 계정의 기본값인데, 화면은 여전히 전역 즉시 적용값처럼 보인다.
5. 라이브 DB에는 현행 계약 32개 외에 **활성 레거시 키 11개**가 남아 있다. 저장 API와 DB 함수가 정규 키·자료형·범위를 엄격히 제한하지 않아 레거시/오타 키가 계속 축적될 수 있다.

따라서 현재 화면은 “저장 성공”을 보여 줄 수는 있어도 “APP 동작 변경 성공”을 보증하지 못한다. 설정 페이지의 노출 항목, 설명, 검증 범위, 초기화 계약을 실제 소비 코드와 다시 맞추기 전에는 운영자가 이 화면을 신뢰해 시스템 동작을 조정하도록 두어서는 안 된다.

## 2. 감사 범위와 판정 기준

### 2.1 검토 범위

- 5개 설정 탭의 필드, 로딩, 저장, 탭별 초기화, 전체 초기화
- `SystemSettingsContext`, `useSystemSettings`, 설정 서비스와 관리자 API
- 대시보드, OEE 표시, 알림, 교대·생산진행, 날짜·시간, 테마 소비 경로
- 최근 설정 관련 Git 변경 이력과 현재 화면 의미의 불일치
- 라이브 Supabase의 활성 키·현재값·DB 함수 권한·배포 Edge Function
- 테스트, TypeScript, ESLint, 마이그레이션 원장 검증

### 2.2 판정 기준

- **완전 적용**: 설정 저장 → 전역 상태 갱신 → 관련 APP 동작까지 일관되게 반영되고 UI 허용 범위가 실행 엔진 지원 범위와 일치함.
- **부분·조건부 적용**: 특정 화면·사용자·프로세스에만 적용되거나, 일부 실행 경로가 별도 하드코딩 값을 사용하거나, UI가 실제 지원 범위보다 넓음.
- **미적용**: 저장은 가능하지만 현재 운영 코드에 소비자가 없거나 효과를 내는 경로가 호출되지 않음.

동일한 기본값이 코드에 하드코딩돼 우연히 화면 결과가 같아 보이는 경우는 “적용”으로 인정하지 않았다. 설정값을 다른 값으로 바꿨을 때 동작이 바뀌는 종단 경로가 있어야 적용으로 판정했다.

### 2.3 방법상 제한

- 사용자 요청에 따라 APP 코드와 실제 설정값은 변경하지 않았다.
- 따라서 운영 데이터를 바꾸는 브라우저 저장 실험은 하지 않았고, 코드 경로·테스트·라이브 읽기 전용 조회로 검증했다.
- 설치된 환경에 `ultrareview`라는 독립 워크플로가 없어 `$code-review`와 `$analyze` 절차로 대체했다. 별도 CLI 리뷰 2개는 10분 제한에서 결과 파일을 만들지 못해, 해당 결과를 근거로 사용하지 않았다.
- 라이브 알림 이메일은 존재 여부만 확인했으며 개인정보·비밀값은 보고서에 기록하지 않았다.

## 3. 최우선 발견사항

### [HIGH-01] 전체 초기화가 실시간 생산 진행 계산을 중단시킬 수 있음

**증거**

- 전체 초기화는 DB의 각 행에 저장된 `default_value`가 아니라 `src/lib/systemSettings.ts:745-1054`의 별도 하드코딩 레지스트리를 사용한다.
- 그 레지스트리의 `break_time_minutes` 기본값은 60분이다 (`src/lib/systemSettings.ts:923-930`).
- 라이브 DB의 현재 휴식시간은 110분이며, 실시간 휴식 스케줄은 고정 합계 110분이다 (`src/utils/shiftBreaks.ts:4-16`, `src/utils/shiftBreaks.ts:28`).
- 생산 진행 API는 설정 휴식시간이 110분과 다르면 `break_config_matches=false`를 반환하고 실시간 계산을 중단한다 (`src/app/api/production-progress/route.ts:233-254`).
- 초기화는 `Promise.all` 기반 비원자적 갱신이다 (`src/lib/systemSettings.ts:571-609`). 중간 실패 시 일부 설정만 초기화될 수 있다.
- 초기화 레지스트리는 제거된 `shift_a_end`, `shift_b_end`는 여전히 포함하지만, 현행 `shift_change_buffer_minutes`와 `notification_email`은 누락한다.

**영향**

- 관리자가 정상적인 “모든 설정 초기화” 기능으로 인식하고 실행하면 실시간 생산 진행 기능이 즉시 안전 중단될 수 있다.
- 일부 키만 바뀌는 부분 초기화 상태가 발생해 APP의 설정 계약을 더 불명확하게 만들 수 있다.

**설정 페이지 변경 필요사항**

- P0: 실제 단일 기본값 원천과 원자적 초기화가 마련되기 전까지 전체 초기화 버튼을 비활성화하거나 위험 경고와 영향 미리보기를 제공해야 한다.
- 레거시 키를 초기화 대상에서 제외하고, 현행 키 32개가 정확히 포함되는지 계약 테스트를 둬야 한다.
- DB 기본값, 코드 기본값, UI 기본값을 하나의 스키마에서 생성하도록 정리해야 한다.

### [HIGH-02] OEE 탭 7개 설정이 모두 APP의 실제 판단 기준에 적용되지 않음

**증거**

- `useOEEThresholds()`는 값을 반환하지만 운영 코드 호출 지점이 없다 (`src/hooks/useSystemSettings.ts:63-67`).
- OEE 게이지는 0.85/0.65를 하드코딩한다 (`src/components/oee/OEEGauge.tsx:56-67`).
- 운영자 대시보드는 0.85/0.65 (`src/components/dashboard/OperatorDashboard.tsx:312-320`), 엔지니어 대시보드는 0.85/0.75/0.65 (`src/components/dashboard/EngineerDashboard.tsx:58-63`), 관리자 대시보드는 0.85/0.65를 사용한다 (`src/components/dashboard/AdminDashboard.tsx:618-625`).
- 알림 API도 OEE·가동률·성능·품질·다운타임 임계값을 하드코딩한다 (`src/app/api/alerts/route.ts:32-53`).
- OEE 탭 로딩은 `||`를 사용하므로 합법적인 저장값 `0`도 기본값으로 치환될 수 있다 (`src/components/settings/tabs/OEESettingsTab.tsx:39-50`).

**영향**

- 관리자는 저장 성공 메시지를 보지만 게이지 색상, 대시보드 상태, 알림 판단은 변하지 않는다.
- 화면별 하드코딩 기준도 서로 달라 동일 OEE 값이 화면마다 다르게 평가될 수 있다.

**설정 페이지 변경 필요사항**

- P0: 소비 경로를 통합하기 전에는 7개 항목을 숨기거나 “현재 미적용”으로 잠그고 저장을 막아야 한다.
- 목표값과 상태 임계값의 의미·단위·우선순위를 명시하고, APP 전체가 하나의 설정 소비 함수를 사용하도록 계약을 정해야 한다.
- `0` 보존을 위해 null 병합 규칙으로 바꾸는 검토가 필요하다.

### [HIGH-03] 알림 탭 5개 설정이 모두 실질적으로 미적용

**증거**

- `getNotificationSettings()`의 운영 호출 지점이 없다 (`src/hooks/useSystemSettings.ts:98-107`).
- 운영 알림 폴링은 고정 60초다 (`src/hooks/useOperationalAlerts.ts:26`, `src/hooks/useOperationalAlerts.ts:60-68`).
- 알림 Context도 고정 60초를 사용한다 (`src/contexts/NotificationContext.tsx:17-20`, `src/contexts/NotificationContext.tsx:535-536`).
- 라이브 DB의 `alert_check_interval_seconds`는 120초이지만 APP은 60초로 동작한다. 이는 기본값 우연 일치가 아닌 실제 미적용 증거다.
- 브라우저 알림 권한 요청은 설정과 무관하게 수행된다 (`src/hooks/useOperationalAlerts.ts:103-106`).
- 현재 코드에는 설정 이메일로 발송하는 운영 경로와 알림음 재생 경로가 없다.
- 별도 `useRealtimeNotifications`도 고정 30초를 사용하지만 운영 호출 지점이 없고 테스트에만 등장한다 (`src/hooks/useRealtimeNotifications.ts:283-294`).

**영향**

- 이메일/브라우저/소리 활성화와 확인 간격을 바꿔도 실제 알림 행동이 달라지지 않는다.
- 운영자는 알림이 제어됐다고 오인할 수 있어 장애 감지와 개인정보 전달 기대가 어긋난다.

**설정 페이지 변경 필요사항**

- P0: 실제 채널 구현과 소비 연결 전까지 탭을 비활성화하거나 각 항목에 “미지원/미적용” 상태를 표시해야 한다.
- 이메일 주소 입력은 실제 발송 기능, 주소 검증, 테스트 발송, 오류 상태를 함께 제공할 때만 노출해야 한다.
- 폴링 주기는 단일 소비 지점으로 통합하고 최소·최대 범위를 서버에서도 강제해야 한다.

### [HIGH-04] 교대 탭이 실제 계산 엔진보다 넓은 값을 허용함

**증거**

- 2026-07-29 변경에서 종료시각 입력을 제거하고 시작시각으로 종료시각을 유도하도록 바뀌었다 (`src/components/settings/tabs/ShiftSettingsTab.tsx:44-54`).
- UI 검증은 두 시작시각이 같지 않고 휴식·버퍼가 계산된 교대 길이보다 짧은지만 확인한다 (`src/components/settings/tabs/ShiftSettingsTab.tsx:73-140`). 따라서 12시간이 아닌 불균형 교대도 저장 가능하다.
- 설비 콘솔은 명시적으로 720분 교대를 전제한다 (`src/components/dashboard/operator-console/MachineConsole.tsx:54-55`).
- 실시간 진행 계산의 휴식 구간은 교대 시작 대비 고정 오프셋이다 (`src/utils/realtimeProgress.ts:66-80`, `src/utils/shiftBreaks.ts:35-45`).
- 휴식시간은 UI에서 0~240분을 허용하지만 실시간 진행 API는 110분만 지원한다.

**영향**

- 저장 자체는 성공해도 교대 판정, 실시간 목표량, 휴식 공제, 대시보드 경계가 서로 다른 모델을 사용할 수 있다.
- “설정 가능한 값”이 곧 “지원되는 값”이라는 UI 계약이 깨진다.

**설정 페이지 변경 필요사항**

- P0: 현재 엔진이 12시간/110분 모델만 지원한다면 UI를 그 값으로 제한하고 제약을 명시해야 한다.
- 가변 교대를 제품 요구로 유지하려면 먼저 모든 계산 경로를 설정 기반으로 바꾸고 자정 교차·비대칭 교대·가변 휴식 회귀 테스트를 마련해야 한다.

### [HIGH-05] 일반·OEE·알림·화면 저장이 원자적이지 않음

**증거**

- 교대 탭만 원자적 배치 저장을 사용한다 (`src/components/settings/tabs/ShiftSettingsTab.tsx:128-146`).
- 일반 탭은 `updateMultipleSettings`를 사용하지만 내부 구현은 `Promise.all` 개별 갱신이다 (`src/lib/systemSettings.ts:476-497`).
- OEE, 알림, 화면 탭은 설정을 순차 저장한다 (`OEESettingsTab.tsx:54-91`, `NotificationSettingsTab.tsx:59-95`, `DisplaySettingsTab.tsx:61-105`).

**영향**

- 후반 키 저장 실패 시 앞선 키는 이미 반영된다. UI는 전체 실패로 표시할 수 있지만 DB에는 부분 변경이 남는다.
- 탭 단위 설정 조합이 불변조건을 가진 경우 중간 상태가 Realtime으로 다른 사용자에게 전파될 수 있다.

**설정 페이지 변경 필요사항**

- P0: 모든 탭 저장을 서버 측 검증이 포함된 원자적 배치 갱신으로 통일해야 한다.
- 실패 응답에는 키별 결과가 아니라 전체 롤백 보장을 제공해야 한다.

### 5.2 레거시가 계속 남을 수 있는 원인

- 관리자 업데이트 API는 카테고리와 키가 비어 있지 않은지만 확인하고 정규 키 whitelist, 자료형, 범위를 강제하지 않는다 (`src/app/api/system-settings/update/route.ts:20-31`).

- DB의 `update_system_setting`은 관리자 권한을 확인하는 점은 양호하지만, 호출자가 보낸 임의 키를 현행 계약과 대조하는 계층이 없다.

**권고**

- 설정 스키마를 `category + key + type + range + default + consumer owner + deprecated`의 단일 registry로 정의한다.
- API와 DB 함수 모두 현행 키만 허용하고, 폐기 키는 읽기 호환 기간 후 마이그레이션으로 비활성화한다.
- 중복 활성 행을 막는 유일성 제약과 마이그레이션 검증을 추가한다.

## 6. 최근 수정 코드와 설정 페이지 불일치

### 6.1 개인 설정 분리 후 라벨이 구 의미를 유지

- 커밋 `d355df1`(2026-07-14)은 언어와 테마를 사용자 프로필 우선, 시스템 설정 fallback 구조로 변경했다.
- 현재 우선순위는 프로필 값 → 시스템 기본값이다 (`src/contexts/UserPreferencesContext.tsx:118-129`).
- 그러나 설정 페이지의 라벨은 여전히 단순 “언어”, “테마 모드”여서 모든 사용자에게 즉시 적용되는 전역값처럼 보인다.

**필요 변경**: “기본 언어”, “기본 테마”가 아니라 더 명확히 “개인 설정이 없는 사용자에게 적용되는 시스템 기본값”으로 설명하고, 현재 사용자 개인 설정이 우선한다는 안내를 표시해야 한다.

### 6.2 교대 종료시각 제거 후 레거시 초기화 계약 잔존

- 커밋 `d0da963`(2026-07-29)은 교대 종료시각 입력을 제거하고 원자 저장을 도입했다.
- 타입과 초기화 레지스트리에는 `shift_a_end`, `shift_b_end`가 여전히 남아 있다.
- 반대로 같은 변경에서 중요해진 `shift_change_buffer_minutes`는 전체 초기화 레지스트리에 없다.

**필요 변경**: 화면·타입·기본값 registry·DB 활성 키를 동일 계약으로 정렬하고, 제거된 항목을 초기화/감사 대상에서 제외해야 한다.

### 6.3 시스템 설정 Realtime 개선 후 설정 의미 검증은 미완료

최근 변경은 설정 변경 신호와 사용자 기본값 hydration을 개선했지만, “설정이 실제 기능에서 소비되는가”를 보장하는 종단 테스트는 추가되지 않았다. Realtime으로 미적용 값을 더 빠르게 다시 읽는 것만으로는 기능 적용이 되지 않는다.

## 7. 설정 페이지 자체의 상태·사용성 결함

### [MEDIUM-01] 미저장 변경 감지가 반대로 동작

- 부모는 `hasUnsavedChanges`로 탭 이동 경고를 구현한다 (`src/components/settings/SystemSettings.tsx:187-204`).
- 각 탭은 입력 변경 시점이 아니라 **저장 성공 후** `onSettingsChange()`를 호출한다.
- 따라서 저장 전 편집에는 경고가 없고, 저장이 끝난 뒤 오히려 미저장 상태가 켜질 수 있다.

**필요 변경**: 폼의 `onValuesChange`와 마지막 저장 스냅샷 비교로 dirty 상태를 계산하고, 저장 성공 시 dirty를 해제해야 한다.

### [MEDIUM-02] 탭별 `초기화`가 로드된 값 복원을 보장하지 않음

- 탭은 비동기 로드 후 `setFieldsValue()`를 사용하지만, 탭별 초기화는 `form.resetFields()`만 호출한다.
- 명시적 `initialValues`/저장 스냅샷이 없어 로드된 DB 값이 아니라 빈 값 또는 컴포넌트 초기 상태로 돌아갈 수 있다.

**필요 변경**: 버튼 의미를 “저장된 값으로 되돌리기”와 “시스템 기본값으로 설정”으로 분리하고, 각각의 목표값을 미리 보여 줘야 한다.

### [MEDIUM-03] `마지막 업데이트`가 실제 DB 변경시각이 아님

- Context는 설정을 읽어 온 시각에 `new Date()`를 기록한다 (`src/contexts/SystemSettingsContext.tsx:63-68`).
- 화면은 이를 “마지막 업데이트”로 표시한다 (`src/components/settings/SystemSettings.tsx:235-239`).

**필요 변경**: “마지막 조회”로 라벨을 바꾸거나 DB의 최대 `updated_at`을 표시해야 한다.

### [MEDIUM-04] 저장 성공과 기능 적용 성공을 구분하지 않음

현재 성공 메시지는 DB 쓰기 성공만 의미한다. 소비자가 없는 OEE·알림·화면 설정도 동일한 성공 메시지를 보인다.

**필요 변경**: 미지원 항목을 먼저 제거하고, 지원 항목에는 적용 범위·재로그인 필요 여부·배치 반영 여부를 명시해야 한다.

## 8. 배포·런타임 교차검증

### 8.1 라이브 Supabase

- 대상 프로젝트는 정상 상태였다.
- 현행 계약 32개 키는 모두 존재했다.

### 8.2 배포 Edge Function

- 라이브 `daily-oee-aggregation`은 active version 2이며 로컬 소스와 같은 `PLANT_TIMEZONE = 'Asia/Ho_Chi_Minh'` 상수를 사용한다 (`supabase/functions/daily-oee-aggregation/index.ts:70-71`).

전체 테스트가 통과해도 미적용 설정을 잡지 못하는 이유는 테스트가 “DB에 저장되는가” 또는 개별 유틸 동작을 주로 확인하고, “설정값을 바꾸면 실제 소비 화면/알림/계산 결과가 바뀌는가”를 검증하지 않기 때문이다.

## 10. 권고 우선순위

### P0 — 운영 위험 차단

1. 전체 초기화 기능을 안전한 단일 기본값·원자 트랜잭션·영향 미리보기 없이 실행하지 못하게 한다.
2. OEE 7개와 알림 5개는 실제 소비 연결 전 숨김/잠금 및 미지원 표시한다.
3. 교대 입력을 현재 엔진 지원 범위(12시간 교대, 110분 휴식)에 맞춰 제한하거나, 엔진 가변화가 완료될 때까지 실험적 설정으로 분리한다.
4. 모든 탭 저장을 서버 검증 포함 원자 배치로 통일한다.

### P1 — 화면과 실제 의미 정렬

1. 언어·테마를 “개인 설정이 없는 사용자의 시스템 기본값”으로 재표현한다.
2. 로고·날짜·시간·차트 애니메이션·설비 이미지·사이드바 항목은 소비 연결 전 제거/비활성화한다.
3. 시간대와 자동 새로고침은 적용 대상과 미적용 경로를 화면에 명시한다.
4. dirty 상태, 탭별 초기화 의미, 마지막 업데이트 라벨을 수정한다.

### P2 — 설정 계약 영구화

1. 단일 typed setting registry를 만들고 UI·API·DB·기본값·문서를 여기서 파생한다.
2. 허용 키, 자료형, 범위, enum을 API와 DB 양쪽에서 검증한다.
3. 활성 레거시 11개를 사용 여부 확인 후 마이그레이션으로 병합·비활성화한다.
4. 각 설정에 “값 변경 → 실제 소비 동작 변경” 종단 계약 테스트를 추가한다.
5. 설정별 소유 컴포넌트와 적용 범위를 감사 화면에서 확인할 수 있게 한다.

## 11. 최종 판정

**REQUEST CHANGES / BLOCK**

현재 설정 페이지는 설정 저장 화면으로서는 동작하지만 APP 전체의 동작을 제어하는 관리 화면으로서는 계약이 깨져 있다. 특히 전체 초기화의 실시간 생산 진행 중단 위험, OEE·알림 설정의 전면 미적용, 교대 UI와 계산 엔진 간 지원 범위 불일치는 운영 전 차단해야 한다.

이번 감사에서는 APP 코드, DB 값, Edge Function, 마이그레이션을 수정하지 않았다. 저장소에 추가한 유일한 산출물은 본 감사 보고서다.
